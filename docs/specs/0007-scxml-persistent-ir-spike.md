## Verdict

**SCXML as an artifact only.** Keep tsukuri's JSON (the 0004 `jsonCodec`, defined by the Effect Schema) as the one persistent form. Emit SCXML from the IR when a statechart tool should show the story: states, parallel regions, Beat transitions, optionally the payload as `rb:` attributes. In 0004's vocabulary SCXML is an `ArtifactRenderer`, never an `IrCodec`.

Reasons, each with a number:

1. **SCXML has no place for what tsukuri stores.** 98.6 % of the IR leaves are foreign content (Q1). The standard's own foreign-content rule is "behavior is undefined" (A.2, in the SCXML catalogue below), and the four tools bear that out (Q3).
2. **The persistent role needs a round trip through other tools, and none gives it.** 0 of 4 tools write the foreign content back. The only gain of persisting as SCXML is that other tools can open the file, and they open the skeleton either way.
3. **The codec costs more than the artifact and buys nothing.** 505 lines mirror a schema that already exists (Q4), an escape layer is required for XML 1.0 (Q5), and in 1,000 random pairs of edits to different facts `git merge-file` reported a false conflict 43 times for the SCXML layout and 5 times for JSON (Q6).
4. **SCXML's semantics do not carry tsukuri's model.** Its time is `send@delay`, which forbidden code surrounds; its transitions are instants; its guards and data are code (SCXML catalogue, rows `cond`, `<datamodel>`, `<send>`). Windowed Beats, curves, exact time and SMIL timing are all `rb:` in any SCXML form.

| Option | Cost | What it gives | Verdict |
| --- | --- | --- | --- |
| A. SCXML persistent | the 505-line mapping and escape layer; `rb:` content needs its own schema (the W3C XSD treats it as `lax` and validates nothing in it); 43 false merge conflicts in 1,000 random pairs of edits (JSON: 5); every 0005 construct lands in `rb:` | files open in 4 tools as a skeleton; payload invisible to them; nothing preserved on save | no |
| B. JSON persistent plus SCXML `IrCodec` | the same 505 lines, kept in step with the Schema by a property test and a drift test (Q4) | lossless SCXML for tsukuri's own use; no consumer that benefits | no, unless a consumer appears (below) |
| **C. JSON persistent plus SCXML artifact** | one-way renderer, about 40 lines [INFERENCE: not built]; no round-trip obligation, so no escape layer and no drift gate | the skeleton in Qt, SCION, XState and Commons SCXML; the `rb:` payload optional (SCION keeps it) | **yes** |

What would change the verdict:

- A maintained SCXML tool that **preserves a foreign namespace on write** and that authors want to use. None of the four does (Q3). Then B becomes worth its cost.
- A requirement to **hand-edit stories in a third-party statechart editor** (Stately, Qt Creator). That needs the payload to survive the editor, so the same condition.
- A **split persistence**: skeleton in SCXML, Element and timing payload in a sidecar JSON keyed by state id. This is cheap to build, but it makes two files one fact, which the single-source rule forbids unless a gate ties them.
- A change in the standard: defined semantics for foreign content (A.2 says undefined today). No sign of it; the Recommendation is from 2015.

### Q1 Coverage

Method: the IR of `stories/same-id` (the 0004 `fountainImporter` and `jsonCodec`, run read-only from `.worktrees/0004`, saved as `spike/scxml/fixtures/same-id.graph.json`) is a tree of 495 scalar leaves. `coverage.ts` classifies each leaf by the construct that carries it, then counts the nodes of the generated document by namespace.

The profile maps the IR like this (`spike/scxml/fixtures/same-id.scxml` is the full output):

```xml
<scxml xmlns="http://www.w3.org/2005/07/scxml" xmlns:rb="urn:tsukuri:ir:1" version="1.0" initial="sc1"
       rb:ir="1" rb:title="Same name, new place" rb:author="tsukuri" rb:speed="1.1">
  <rb:chapter id="ch1" line="7" title="Two screens" synopsis="..."><rb:scene ref="sc1"/>...</rb:chapter>
  <state id="sc1" rb:chapter="ch1" rb:heading="INT. TITLE CARD - DAY" rb:line="11" rb:transition="default">
    <rb:element cell="mc" class="title" id="title" line="13" text="Same name, new place" visible="true"/>
    <rb:line id="sc1.l1" line="18" pause-before="0" speed="0.99" text="Here is a small idea..."><rb:w v="Here"/>...</rb:line>
    <rb:effect id="f1" line="71" verb="focus" target="hint" written="..."><rb:when><rb:shift>...</rb:shift></rb:when></rb:effect>
    <transition event="rb.next" target="sc2"/>
  </state>
  ...
</scxml>
```

| IR construct | Class | Where it lands |
| --- | --- | --- |
| Scene (id, order) | **native** | `<state id>`, document order, `initial` |
| Beat between two Scenes | **native (structure only)** | `<transition event target>`; the target is derived from the order and carries no fact |
| Story (title, author, speed, IR version) | foreign | `rb:` attributes on `<scxml>` (SCXML's own `version="1.0"` is not the IR version) |
| Chapter | foreign | `rb:chapter`. Nesting Scenes in compound states is unsafe: the Schema does not tie `chapters[].sceneIds` to `scenes[].chapterId` or require contiguity |
| Scene properties (heading, source line, incoming transition kind, chapter) | foreign | `rb:` attributes on `<state>`; with 0005 the kind moves onto the Beat edge, still an `rb:` attribute |
| Elements (cell, class, text, visible, line) | foreign | `rb:element`; SCXML has no notion of payload on a state |
| Lines (text, speed, pause, words) | foreign | `rb:line`, `rb:w` |
| Effects (verb, target, `when`, `until`) | foreign | `rb:effect` with the event-expression tree as `rb:` elements |
| Event expressions (`all`, `first`, `each`, `within`, `shift`, anchors) | foreign | `rb:` element tree. SCXML's only expression language is `cond`/`expr`, which is code and forbidden |
| State and edge events (`one.move.start`, `state(2).enter`) | **not representable** natively | SCXML has `onentry` and `onexit` only as executable content (code) |
| Derived events (`let`) | foreign | `rb:event`. SCXML's `<raise>` is executable content |
| Machines (presence, position, style, effect, slide, beats) | not stored | generated by the engine, not part of the IR; SCXML `<parallel>` could declare them |
| 0005: a windowed transition (Beat with a duration) | **not representable** natively | SCXML transitions are instants; a window is two instants and a `during` state |
| 0005: curves and the expression language | foreign | `rb:` expression tree; `cond` and `expr` are code |
| IR time (flicks, exact) | foreign | `rb:` attributes. SCXML's `delay` is a CSS2 time on `<send>` (forbidden), and 1 flick is 1/705,600,000 s, which has no finite decimal (705,600,000 = 2^9 x 3^2 x 5^5 x 7^2, so the primes 3 and 7 make the decimal infinite) |
| Strings with U+0000 to U+001F (but tab, LF, CR), lone surrogates, U+FFFE or U+FFFF | **not representable** in XML 1.0 | the codec escapes them (`\u{hex}`); see Q5 |

### Q2 Profile

The profile allows only what the skeleton needs and the Null data model of the SCXML Recommendation (Appendix B.1, "Minimal Profile") already permits, plus the `rb:` namespace.

| Element or attribute | Profile | Why |
| --- | --- | --- |
| `scxml` (`version`, `initial`, `xmlns`) | allow | root |
| `state` (`id`), `parallel`, `final` | allow | the skeleton |
| `transition` (`event`, `target`, `type`) | allow | Beats and structure |
| `initial` attribute | allow (one id) | |
| `rb:*` elements and attributes | allow, closed list | the IR payload |
| `datamodel`, `data`, `assign`, `script`, `donedata`, `content`, `param` | **forbid** | data and code |
| `send`, `cancel`, `invoke`, `finalize` | **forbid** | external I/O; nondeterministic |
| `onentry`, `onexit`, `raise`, `if`, `elseif`, `else`, `foreach`, `log` | **forbid** | executable content |
| `transition@cond`, `send@delay`, `scxml@datamodel`, `scxml@binding`, `src` | **forbid** | expressions and data |
| `history`, `<initial>` element | forbid for now | deferred (SCXML catalogue) |
| any other namespace, any unknown attribute | **forbid** | A.2: undefined behaviour |

Can a schema reject the forbidden ones? Three mechanisms, same documents (`bad-*.scxml` made by editing `same-id.scxml`; commands in Reproduction):

| Document | Effect Schema profile (`profile.ts`, closed, `onExcessProperty: "error"`) | W3C XSD, full driver (`scxml.xsd`) | W3C XSD, restricted driver (`profile-driver.xsd`) |
| --- | --- | --- | --- |
| `same-id.scxml` | accepts | **valid** | valid |
| `<script>` inside `<onentry>` | **rejects** | valid | **rejects** |
| `<send>` inside `<onentry>` | rejects (`onentry` not declared) | valid | **rejects** |
| `<log>` inside `<onentry>` | rejects | valid | **rejects** |
| `<datamodel>` at the root | **rejects** | valid | **valid** (hole) |
| `<script>` at the root | rejects | valid | **valid** (hole) |
| `<invoke>` in a state | rejects | valid | **valid** (hole) |
| `cond="1==1"` on a transition | **rejects** | valid | **valid** (hole) |
| unknown attribute in the SCXML namespace | rejects | rejects | rejects |
| unknown `rb:` element | **rejects** | valid (`processContents="lax"`) | valid |

Findings: (1) **Yes, by schema rather than code**, with an Effect Schema over the element tree: a closed union of element shapes makes every forbidden element or attribute a decode error. All 13 forbidden forms of `src/profile.test.ts` (`script`, `send`, `log` and `raise` in `onentry` or `onexit`, `invoke`, `datamodel` and `script` at the root, `cond`, `scxml@datamodel`, `history`, an unknown `rb:` element, an unknown SCXML attribute, a foreign-namespace element) are rejected with a `SchemaError` that names the path, and the generated document is accepted (`results/profile-test.txt`: 14 pass). (2) The **W3C modular XSD cannot be profiled by dropping modules**: `scxml-module-core.xsd` references `param` (data module) and `invoke` (external module), so a driver that includes only the core module does not compile (`xmllint`: "The QName value ... param does not resolve"). A driver must include all three modules and restrict only the executable-content group, which leaves the holes above, or the XSD must be forked. (3) The XSD never validates `rb:` content. Whatever the form, a profile needs one schema of its own, and the Effect Schema is the one that is already there.

Raw output of every XSD row, and the compile failure of the core-module-only driver, is `results/interop-xsd.txt` (`sh interop/run-interop.sh`).

The XState question: **v5 has no SCXML import** (`xstate@5.33.3` tarball: no file with `scxml` in its name; its text mentions SCXML only in comments); v4 had `xstate/lib/scxml.js` (checked in 4.38.3); v6 brings it back as the separate `@xstate/scxml` package (`docs/scxml.md` of `xstate@6.0.0-alpha.71`), (the package's npm `modified` time is 2026-10-29). A finding from the first run: **Commons SCXML reads attributes by local name**. The document first carried `rb:version`, and the reader rejected it as `unsupported version "1"`, because it took the foreign attribute for SCXML's `version` (reproduced: `results/interop-commons-collision.txt`). ### Q4 Single source

Question: can the XML form be derived from the Effect Schema, with a Schema transformation to an XML element tree plus a maintained parser and serialiser at the boundary, so that no hand-written XSD duplicates it?

**Answer: yes for validation, only partly for the shape.** Three layers, measured:

| Layer | What it is | Hand-written | Drift risk |
| --- | --- | --- | --- |
| Tree and profile | `XmlElement` plus `profile.ts`, an Effect Schema of closed element shapes (131 lines) | the profile | a new IR field is missing from the profile |
| Mapping | `graphToTree`, `treeToGraph` (`codec.ts`: 303 lines of mapping, 71 of escape and entry points) | the mapping | a new IR field is silently dropped (below) |
| Boundary | `parseXml` (saxes), `printXml` (30 lines) | the printer | none |

Total about 505 lines of TypeScript mirror `graph.ts` and `plan.ts` (631 lines in full; `results/xml-libs.txt`). **Drift test** (`sh src/drift.sh`, `results/drift.txt`): adding an optional field `note` to `ElementSchema` in a copy of `plan.ts` makes the idiomatic codec lose it silently, and the property test falsifies it after **651 runs** (1,000 requested, seed 7; an earlier run at 300 requested runs stopped after 196, so the count depends on the run budget, not only on the seed). The control (JSON), the escape-less codec test and the generic structural codec still pass, 3 of 4. A required field would be flagged the same way. The mapping uses a loose `any` for IR values on purpose (a spike); with typed values a required field would also fail the type check, an optional one would still need the test.

**The zero-mapping alternative exists**: `generic.ts` (78 lines) derives the XML from the _value_ (a Parker-style structural encoding), so nothing is written per field and nothing can drift. It holds the same round-trip law over 1,000 runs. Its document is 57,027 bytes and 1,688 lines for `same-id` (3.2 times JSON) and is 100 % `rb:`: a JSON file in an XML coat, with one `<state>`. This is the honest bound: **derivation is free exactly when the result does not use SCXML's vocabulary**.

An XSD is not needed for the codec: decode validates through the Effect profile and then through `GraphSchema` (so a hand-written XSD would be the duplicate). The document validates against the **W3C** XSD (`xmllint --schema scxml.xsd`: valid), so no tool is lost by omitting one.

### Q5 Round trip

`spike/scxml/src/roundtrip.test.ts`, run with `bun test`: `Arbitrary.schema(GraphSchema)` (Effect 4.1.0's own) generates Graphs, `Arbitrary.checkEffect` runs the property, and `Schema.toEquivalence(GraphSchema)` is the judge. Generator coverage (`results/generator-stats.txt`, 300 samples): 1,503 Scenes, 7,417 effects, 3,690 with `until`, 3,758 with an absolute time, all expression kinds (`ref` 3,366, `all` 3,235, `first` 3,371, `each` 3,452, `within` 240, `shift` 191) and all three anchor kinds.

| Test (1,000 runs, seed 7) | Result |
| --- | --- |
| control: the JSON codec on the same generator | pass |
| `decode(encode(ir)) = ir`, SCXML profile codec | **pass** |
| the same codec **without** the escape layer | **falsified after 52 runs**; shrunk input: a Scene whose `id` and `chapterId` are `"\u0000"` |

| mutation: drop the last word of a Line | falsified after 52 runs |

The escape layer exists because the IR Schema accepts any `String` and XML 1.0 cannot hold some code points even as character references. It rewrites `\` as `\\` and each unrepresentable code point as `\u{hex}`. This is a property of XML, not of the codec: JSON carries them with one escape of its own.

### Q6 Ergonomics

Sizes for `stories/same-id` (`results/ergonomics.txt`):

| Format | Bytes | Lines | Gzip |
| --- | --- | --- | --- |
| JSON (0004 `jsonCodec`) | 17,675 | 785 | 2,445 |
| SCXML profile | 11,726 | 281 | 2,328 |
| generic structural XML | 57,027 | 1,688 | 3,239 |

**Typical edits** (`git diff --no-index -U1`): moving an element (`box`, cell `ml` to `mc`) changes 2 lines in every format. Retiming an effect (`f1`, `-0.2 s` to `-0.3 s`) changes 4 lines in every format: the exact offset (flicks) and the `written` text. In SCXML the `written` change sits in the long opening line of `<rb:effect ... written="word(&quot;slides&quot;).start -0.3s" target="hint">`, with the entities of an attribute.

**Concurrent edits.** 1,000 random pairs of single-leaf edits to _different_ leaves (137 editable leaves: booleans, cells, classes, line numbers, offsets), merged with `git merge-file`. Every conflict is false: the two edits touch different facts.

| Format | False conflicts of 1,000 |
| --- | --- |
| JSON | **5** (0.5 %) |
| SCXML profile | **43** (4.3 %) |
| generic structural XML | 0 |

The cause is layout: the SCXML profile packs the attributes of one element on one line (an element's `cell` and `class` edited by two people conflict), JSON puts one leaf on one line but adjacent leaves can still collide, and the generic form spreads every leaf over three lines.

**CRDT fit.** [Yjs `Y.XmlElement`](https://docs.yjs.dev/api/shared-types/y.xmlelement) has a `nodeName` and string-only attributes (`setAttribute(name, value: string | Y.AbstractType)`, observed as a `Y.Map`-style event) and children as an ordered fragment; [`Y.Map`](https://docs.yjs.dev/api/shared-types/y.map) takes "anything json-encodable", typed. Both map the IR. XML attributes are strings, so every number and boolean is stringly typed and needs a codec at the edit boundary; `nodeName` is fixed, so turning `rb:all` into `rb:first` is a delete and an insert in XML and one key update in a map. The IR is a tagged-union tree, which suits a typed `Y.Map` and `Y.Array` better. Neither is a reason to persist as SCXML; both are a reason to keep JSON.

## Construct catalogue

Reading the tally: SMIL is mostly **adapted**, because its timing is the right algebra over a model (one current interval, wall-clock, DOM events) that tsukuri replaces with exact plan-time resolution. #### Gaps and surprises

1. **Naming.** SMIL 3.0 spells `endsync` as `first`, `last`, `all`, `media`, or an Id-value (and deprecated `id(Idref)`); there is no `all-ids`. 0004's table maps its `all` to `endsync="all"`, but its definition (`max` over operands) is `endsync="last"`. `all` and `last` differ only when a child has an unresolved begin, which tsukuri forbids.
2. **`until` and equal frames.** 0004 ignores an end occurrence equal to the start. SMIL's interval algorithm (`getFirstInterval`) takes the first end value `>=` the begin and handles a zero-duration interval with a special case. Also SMIL never lets one event occurrence both begin and end an element (5.4.5 Event sensitivity). 0004 needs a rule for `each(e)` with `until each(e)`.
3. **Instances.** SMIL has one current interval per element, and clears event begin times at begin (5.4.6). 0004 makes one instance per occurrence, never cleared. This is a real departure, and needs `restart: overlap` plus the row *Begin-value list* fixture.
4. **Time quantisation.** 0004 defines time as an integer frame; the operator decision is exact time. Equality tests (`until`, `throttle`, the zero-duration case) change if two times land on one frame. Evaluate the algebra on exact times, quantise only at render, and use the half-open `[begin,end)` rule with `ceil(t*fps)` for the first visible frame. At 30 fps one frame is 23 520 000 flicks `[derived]`.
5. **Negative offsets.** `word("slides").start -0.2s` can precede the Scene begin. SMIL defines this (cut off, dependents use the computed time, first iteration only); 0004 does not.
6. **Implicit duration trap.** Discrete media has implicit duration 0 and `fill="auto"` makes it vanish (Example 4). Require an explicit dwell; take `media` duration from the Line asset.
7. **Open cycles** (ping-pong) are an intentional SMIL feature, banned here; the cost is that authors must unroll with `repeat`.
8. **Lazy interaction = two renderers.** `dur="10s" end="activateEvent"` fits the Deck (a step event) and the Video (the scheduled time): one declaration, two renderings. It maps onto Beat boundaries.
9. **`syncMaster` in spirit.** The Line audio already drives Beat durations; no runtime sync is needed because the video is sampled.
10. **One construct for time warps.** `speed`, `accelerate`, `decelerate`, `autoReverse` act on a *container's* time and cascade. Planned 0005 curves act on an attribute. Use the same `timeFilter` object for both.
11. **Audio and `speed`.** SMIL's fallback is "best effort" player behaviour, which is not deterministic; tsukuri must forbid `speed != 1` over audio.
12. **Reset on container repeat** (5.4.3 *Resetting element state*): event and DOM times are cleared, syncbase times kept. A looped Scene needs the same rule; SMIL's own Example 4 of the cycles section is flagged "not supported".
13. **Dependents of a cut-off interval** still get computed times: in `<par begin="-10s" dur="20s">` with `slide2 begin="slide1.end+3s" dur="10s"`, "slide2 will be shown ... for 6 seconds, from 0 seconds to 6 seconds" (frames `[0,180)`) although `slide1` never shows. 0004's `x.end` of an interrupted effect needs the same rule.
14. **`excl` as XOR state, `pause` as history.** `[INFERENCE]` Both map to statechart constructs (exclusive compound state, history state); the SCXML section of this report should confirm.

- Caveat: IRP index 1.2 states "The IR does not attempt conformance testing of implementations". It is an interoperability report, not a conformance suite. Use it as a fixture source, not as a pass criterion.

#### Gaps and surprises

1. **The profile boundary already exists in the spec.** B: processors "MUST support the null data model". B.1 gives `In()` only and no system variables; B.1.7 excludes `<foreach>` and the section 5 elements. A tsukuri profile "Null model plus exact time" is a conformant subset, not a fork.
2. **Time is nearly absent in SCXML.** `delay` (6.2.2) is the only time notion. No clock or tick is defined: the spec says dispatch "only when the delay interval elapses". The microwave examples fake a clock with `time` events ("seen once a second"). The XSD `Duration.datatype` pattern is `\d*(\.\d+)?(ms|s|m|h|d)`, wider than the prose "CSS2" (assuming CSS2 times are `s`/`ms`: `[INFERENCE]`, CSS2 not opened). Tsukuri's exact rationals and flicks fill a real gap.
3. **Timers are not scoped in SCXML.** A delayed send survives leaving its state and dies only with the session (6.2.3) unless `<cancel>`led. Tsukuri should scope an offset-event to the source's occupancy.
4. **Offline order of simultaneous external events is undefined.** SCXML has no rule for equal arrival; a plan-time resolver needs (frame, document order). This was found in the Rec, not the IRP.
5. **Finite state space makes macrostep termination decidable.** D "Termination": "A macrostep may not [terminate]. … This is currently allowed." With only `In()` guards and no data, the zero-time eventless graph is finite, so a cycle is a static lint (F8) `[derived]`. With a datamodel it is undecidable in general.
6. **0004 and SCXML differ in five places.** (a) `first(...)` is earliest in time; SCXML picks by document order among *simultaneously* enabled edges. (b) 0004 `each` keeps equal frames once; SCXML takes both non-conflicting edges of parallel regions. (c) 0004 "instances do not restart each other" versus an SCXML external self-transition, which restarts (exit then entry): restart must be an explicit `type:"external"`. (d) 0004's timed `Transition{from,during,to}` is two instants through a state, so a Beat is a configuration member, not just an edge. (e) the `slide` interrupt is a rule in 0004 but structural in a compound Scene (3.13: exiting exits descendants).
7. **`done.invoke` solves "wait for an unknown duration".** Tsukuri knows each Line's duration from alignment (resolved at plan time), so it needs no runtime join. `all(...)` of 0004 already equals `done.state.p`.
8. **Multi-id `initial` (IRP 364, 413, 576) and `<history>` earn no place now.** Both are exotic for a linear Story. Deferred, not rejected.
9. **Errata seen in the Rec text:** 3.12.1 lists `error.send` as both matching and non-matching; the 3.1.3 example is not well-formed (`<state id=S21">`, `target="S2Final/>`); the 3.1.5 internal example has `<log expr="entering S1"/>` with no quoting; G.5 uses `<onenter>`. In addition `exmode` (lax or strict) appears in `scxml-module-core.xsd` but nowhere in the Rec text (0 hits), and the XSD defaults `datamodel` to `"null"` against the prose's "platform-specific".
10. **Document order is a real semantic.** Priority, entry order, handler order and conflict resolution all depend on it. JSON arrays carry it, but any codec that sorts keys (a canonical-JSON hasher) must never reorder them: add a schema note and a round-trip fixture `[derived]`.
11. **Harness shape worth copying.** The IRP is one test file per fact, pass iff final config `{pass}`, with a stylesheet to specialise it. Tsukuri can ship fixtures as `{id, source:"irp-387", chart, expect:{final:"pass", trace:[…]}}`, with the trace of generated `state.enter` and `state.leave` replacing `<raise>`-based observation.

### FRP: Fran (Elliott & Hudak 1997) construct catalogue

**Sources read.** F97 = Elliott & Hudak, *Functional Reactive Animation*, ICFP 1997 (PDF text is font-garbled, so I OCR'd it and checked every quoted line and section/page number against the page images). PP09 = Elliott, *Push-pull functional reactive programming*, Haskell Symposium 2009 (text extracted). TUT = Elliott, *Composing Reactive Animations* (1998 tutorial, <https://conal.net/fran/tutorial.htm>; it has no heading anchors, so I cite heading names). LIB = `conal/Fran` at commit `a113693` (<https://github.com/conal/Fran/tree/a113693cfab23f9ac9704cfee9c610c5edc13d9d/src>), a 2019 import of the Hugs-era sources, read for names the paper lacks. F97 sections: 1 Introduction ("The Essence of Modeling", p.2), 2 Formal Semantics (2.1 Semantic Domains pp.2-3; 2.2 Semantics of Behaviors pp.3-4: *Time, Lifting, Time transformation, Integration, Reactivity*; 2.3 Semantics of Events pp.4-5: *Event handling, Constant events, External events, Predicates, Choice, Snapshot, Event sequencing*), 3 Some Larger Examples pp.5-6, 4 Implementation (4.1 Representing Behaviors p.7; 4.2 Implementing Events pp.7-8), 5 Related Work pp.8-9, 6 Conclusions p.9, Appendix A p.11.

**Semantic model, as the sources state it.** F97 §2.1 p.3: `at : Behavior_α → Time → α`, so a behaviour is a function of time. In F97 an event is a **single** occurrence: `occ : Event_α → Time × α`, described as "non-strict Time x α pairs". The model `type Ba = T → a` and `type Ea = [(T̂, a)] -- for non-decreasing times` is **PP09 §2, p.2**. PP09 says why: "Orginally, FRP had a notion of events as a single value with time, which led to a somewhat awkward programming style with explicit temporal loops (tail recursions)" (p.2; the spelling "Orginally" is the paper's). Time is `Time = R + R>` with partial "at least t" elements (F97 §2.1 p.3); the real line is "≤"-extended so that `t ≤ >y` when `t ≤ y`. The `untilB` semantics (F97 §2.2 p.4) is `if t ≤ t_e then at[b]t else at[b']t`; PP09 §2.3 (p.4) has `before os t = [a | t̂a < t]`. Both say: **at the instant of the occurrence the old behaviour still holds; the new one starts just after.**

**Not in either paper (grepped in both texts and in LIB).** `bmatch`, `colorBFor`, `slowdown`, `delay`, `=>>`, `withElem`, `when :: Behavior Bool -> Event ()`, `lift3` as a named operator. F97 has `lift_n` only as a family. Where LIB has a near relative I say so in the row; otherwise the row says `not in the source`.

**Sketch conventions (proposed, not spec).** Frame `n` at 30 fps is `t = n/30` s exactly (23,520,000 flicks per frame). An attribute expression is a number, `"t"` (exact seconds since the owning State's first frame), `"u"` (Beat progress 0..1) or `[op, args…]`. Events use the 0004 grammar. Numbers marked `[derived]` come from a throwaway binary64 script (not committed), never from a source. `[INFERENCE]` marks a claim I did not verify in a source.

#### Gaps and surprises

- **Event model conflict.** F97 events are a single occurrence; the list model tsukuri uses is PP09's. PP09 allows simultaneous occurrences and a left-biased `merge`; 0004 forbids them (strictly increasing frames). Decide one tie rule and write a fixture for it.
- **Boundary convention conflict.** Both papers keep the **old** behaviour at exactly `t_e` (`t ≤ t_e`; `before … t̂a < t`). 0004's occupancy intervals and SMIL's half-open `[begin,end)` show the **new** state at the event's frame. Every `untilB`, `stepper`, `count` fixture above differs by one sample here.
- **The paper and its published source disagree.** F97 §4.2 says predicate events are found robustly by interval analysis and §4 says integration is RK. In `conal/Fran@a113693` the active `predicate` checks once per display update (`BehaviorEvent.hs:77-80`, "Check once per update") and the active `integral` and `derivative` sample at `updateDone` (`Integral.hs:35-64`); the RK code is commented out (`Integral.hs:92-201`). Treat the semantics as the spec and the implementation as a counter-example for "video = pure function of frame number".
- **Names the task listed that are in neither paper nor LIB:** `bmatch`, `colorBFor`, `slowdown`, `delay`, `=>>`, `withElem` (LIB has `withElemE`), `when :: Behavior Bool -> Event ()` (LIB has `whenE :: Event a -> BoolB -> Event a`, `BehaviorEvent.hs:68`). I did not invent definitions for them.
- **Gating an event by a behaviour (`whenE`) earns a place.** LIB `e \`whenE\` b` keeps occurrences of `e` while `b` is true ("Snapshot condition, test and discard"). In tsukuri: `when(e, cond)` with a closed `cond` or `in(state)`. 0004 has `within(e, beat(k))` only.
- **Periodic source.** LIB [`Event.hs:306`][ev] `alarmE t0 dt` (`[t0+dt, t0+2*dt ..]`): tsukuri has no `every(d)` source; it must be bounded by the Scene end to stay finite.
- **Concurrency.** F97 §1 p.2 ("concurrency (parallel composition) is expressed naturally and implicitly") and PP09 p.3 (`<*>` is "semantically determinate, synchronous, and continuous") support parallel regions that are sampled at one instant.
- **No sound in Fran.** F97 §6 p.9 lists "extending the ideas to 3D graphics and sound" as future work. The sound track as a parallel region has no FRP source to cite.
- **Time transform only on closed curves.** F97 §4.1 (loss of generality) and LIB's `error "timeTransform for GBehavior (Event) not available"` both say it does not compose with reactive behaviours.
- **Pre-start sampling.** `time - 2` samples `b` at negative time. Fran has no pre-start rule; the IR needs one (proposed: clamp to local `t = 0`).
- **Cross-reference (SCXML section).** `condB` over machine state is SCXML's `In()` predicate; `untilB` is a guarded transition; Fran has no history/compound-state counterpart.

### 1. Interpreter at build time

Generator output is a data-only `MachineJSON`: root parallel state with regions `scenes` (Scene = compound state; States = atomic states with `after` dwell; Beat = `s(k) -> b(k) -> s(k+1)`; final `end` + `xstate.done.state`), `elements` (presence/position/style per Element) and `sound` (a voice per sound name). | XState decides | Shown by |

### 2. Codec

Verdict: **round-trippable as a container, output-only as a source of truth.** v6 has `machineFromJSON(json, sources)` / `machineToJSON(machine)` (`MachineJSON`), https://stately.ai/docs/xstate/v6/serialization (that page still names them `serializeMachine` / `createMachineFromConfig`; they were renamed in alpha.68, https://github.com/statelyai/xstate/blob/next/packages/core/CHANGELOG.md).

- The generated config is only strings, numbers and plain objects: 0 function/symbol/bigint/`undefined`/class-instance paths, 0 `@code`/`@expr` objects after `machineToJSON(machineFromJSON(json))`. The only implementation it needs is the named action `mark` (caller-supplied; `@xstate.emit` could replace it, not tested). Built-ins used: `@xstate.raise` with `delay`, `matches`, `after`, `always`, `xstate.done.state`, `meta`.
- `JSON.stringify` of the config: 41,135 bytes; text round trip, `machineToJSON(machineFromJSON(...))` round trip and `decode(encode(ir)) == ir` (direct, via text, via machine) all true (canonical key order).
- The contrast, from the same API: a config with `onDone: ({event}) => ({...})` and `entry: (_, enq) => ...` serializes to `{"@code": "({ event }) => ...", "@lang": "ts"}`: 2 code expressions for 2 functions, not portable. Use only the data form.
- Why not authoritative: `decode` reads only the scene order (the `initial` + `xstate.done.state` chain) and `meta` (Elements, Lines, effects, chapters: 9,504 of 41,135 bytes, 23%). Changing an `after` delay leaves `decode` unchanged (`decodeIgnoresStructure: true`); changing `meta` changes it. The other 77% is timing derived from IR + speech. So the IR stays the source; the machine is a compiled artifact. Docs list v6 features with no JSON form: state `input`, `enq.listen`/`subscribeTo`, `choice` functions.
- SCXML: `@xstate/scxml@1.0.0-alpha.4` (MIT, peer `xstate ^6.0.0-alpha.71`, needs `saxes`) exports only `createMachineFromSCXML` (SCXML in). XState has no SCXML out, so SCXML output stays ours, consistent with "SCXML as codec/output only". Prior art: https://github.com/statelyai/schema (not on npm) maps MachineJSON <-> a Stately spec and has SCXML schemas.

### 5. Recommendation

**Agree, with two changes.** Core stays pure; XState lives in an adapter behind a service. Evidence: the machine config, event names (`xstate.done.state`, `xstate.after`), state ids (`story.scenes.sc1`), effect addresses (`root/actions/mark`) and four renames in one release are all XState vocabulary; none may cross the boundary.

1. **Use the pure system API, not `@xstate/effect`, behind the service.** The pure `advanceSystemTime` produced the same 115-line log as `createEffectActor` + `TestClock`, in 21 ms versus 29 ms, with 133 KB instead of 250 KB bundled (43 vs 85 KB gz), and without a second alpha package whose own cadence is 8 releases in 40 days and which needs a `TestClock` from `effect/testing` in a production path. `@xstate/effect` earns its place only for invoked Effect services, which a build-time interpreter does not need. The pure API is flagged "experimental" in `docs/system-transitions.md`.
2. **Tier placement.** `core` (library): Graph IR, SMIL resolution, identity diff, the resolved `Statechart` data (States/Beats/Scenes with exact intervals), frame math. `services`: a `StatechartInterpreter` tag plus a contract suite. A new integration package (`statechart-xstate`, may depend on services + libraries only): generator `Statechart -> MachineJSON`, `xstate` as its only dependency. The generator belongs in the adapter because it is written in XState vocabulary; the vendor declarations of `machines.ts` should generate the Element regions so they stay one source (today I re-encoded presence/position/style by hand in `generate.ts`).
3. **Interface a hand-written interpreter could implement** (small, and nothing XState-shaped): `interpret(statechart): ReadonlyArray<GeneratedEvent>` with `GeneratedEvent = { atMs, kind: 'scene.enter'|'scene.leave'|'state.enter'|'state.leave'|'beat.start'|'beat.end'|'element.*'|'sound.start', id }` in a total order, and `configurationAt(statechart, atMs): Configuration` (the set of active State/Beat ids). The contract test is what I ran: byte-equal logs across interpreters (3 XState drivers already agree) plus the 7 semantics demos (entry/exit order, same-deadline order, done.state, history, eventless). Since time is resolved by us before XState sees it, a sweep over resolved intervals could replace XState; [INFERENCE] about 100 lines, not built, so the swap is untested.
4. **What leaks:** the id grammar (`.` is a path separator; tsukuri's `idPattern` excludes it, so no collision today); XState's ordering of same-ms events becomes part of the contract (the contract suite must pin it); zero-width Beats and overlapping Beats need our own rule; graph tooling does not see time or delayed raises, so path analysis has to run on our `Statechart`, not on the XState machine (`getSimplePaths` gives 4,608 paths for a 1-path story unless filtered).

**Duplicates of 0004:** XState's machines/regions duplicate the lifecycle machines in `machines.ts` (presence, position, style, effect, slide, beat); XState's events (`xstate.after`, `done.state`) are a second event vocabulary beside 0004's `state.enter/leave`, `beat.start/end/progress`. XState has no `progress`; that stays 0004's.

**Conflict with "the Video is a pure function of the frame number":** the actor APIs (`createEffectActor`, `createActor`) are clock-driven, stateful and replay from the start; deterministic under `TestClock` (20/20) but frame n is only available after running to n. The pure API does not conflict: `advanceSystemTime(initialSnapshot, { time: n * 1000 / fps })` matched the declared State/Beat at every frame, 0 mismatches over 1,330 (24 fps), 1,662 (30 fps) and 3,324 (60 fps) frames, sequentially and by random access from t = 0 (every 8th frame). Cost: random access 5.4-6.8 ms median per frame (max 63.5 ms), sequential 14-19 us. So fps stays a render setting; frames -> ms is ours. Risks: that API is experimental, and a render that samples per frame should keep sequential snapshots, not replay from 0.

Not verified: Stately Studio/visualiser rendering; the hand-written interpreter; behaviour of any alpha beyond 70/71 and of `@xstate/effect` beyond alpha.9/10.

## Findings for 0004 and 0005

These came out of encoding the IR and reading the sources; each is a fact for the owner of 0004 or 0005, not a change made here.

1. **0004 names `all` after the wrong SMIL value.** Its table says `all` is `endsync="all"` but defines it as the maximum over the operands, which is SMIL's `endsync="last"` (SMIL spells the values `first`, `last`, `all`, `media` or an Id-value; there is no `all-ids`). See the SMIL section, Gaps 1.
2. **Instances: 0004 departs from SMIL.** SMIL keeps one current interval per element and clears event begin times when the element begins; 0004 makes one instance per occurrence and never restarts. This is a real choice, to be written as `restart: overlap` (SMIL section, Gaps 3).
3. **Events and equal frames.** 0004's Event is a strictly increasing list of frames; Elliott's list model allows simultaneous occurrences with a left-biased merge. The conformance test must say which tsukuri means (FRP section, row Event). 0004's `until` ignores an end equal to the start; SMIL's interval algorithm takes the first end value at or after the begin.
4. **The IR is stored in frames but decided as exact time.** Equality tests (`until`, `throttle`, zero-duration events) change if two exact times land on one frame. Evaluate the algebra on exact times and quantise at render (SMIL section, Gaps 4).
5. **The Schema is looser than the model.** (a) `Id` is `Schema.NonEmptyString` while `plan.ts` also declares `idPattern` (a letter, then letters, digits, `_`, `-`); SCXML ids are XML names, and the generator produces ids such as `"\u0000"`. (b) `chapters[].sceneIds` and `scenes[].chapterId` say the same thing twice and nothing ties them. (c) `lines[].words` is derivable from `text` (27 % of the leaves of `same-id`) but is stored and unchecked. (d) `written` repeats what the parsed expression already says. Each is a place where two copies can disagree.
6. **Time in SCXML is not scoped.** A delayed `send` survives leaving its state and dies with the session unless cancelled; tsukuri should scope an offset event to its source's occupancy (SCXML section, Gaps 3).
7. **The offline order of simultaneous external events is undefined in SCXML.** A plan-time resolver needs a rule: (frame, document order) (SCXML section, Gaps 4).
8. **A Beat with a window is two instants and a state.** SCXML transitions are instants; 0004's `{from, during, to}` already reifies the window as a `during` state. The XState adapter must do the same (XState section, 1).

## Decisions and open forks

Decisions taken after this report was drafted, all by the operator, 2026-10-29:

1. **Persistent format**: JSON, defined by tsukuri's own Effect Schema. SCXML is not persistent (this report's verdict).
2. **Adopt set**: ratified with the smaller v1 above.
3. **XState**: use the **pure system API** (not `@xstate/effect`), at `xstate@6.0.0-alpha.71` pinned exactly, in an integration package behind a `StatechartInterpreter` service; this belongs to spec 0005. Alpha types never appear in tsukuri's public API. The contract suite of the Q-XState section 5 (byte-equal logs across interpreters plus the semantics demos) is what a hand-written interpreter must pass.
4. **SCXML renderer**: not built now. The artifact stays an option (about 40 lines [INFERENCE]); the spike's profile is the starting point if it is wanted.
5. **Spike code**: pushed to `origin` as `spike/scxml-ir-code` (`b0861af`); it vendors a copy of the unmerged 0004 schema, which is acceptable because this repository is public and 0004 will be too.

Still open, none blocking:

1. **Time model**: exact time as the IR's truth with the algebra evaluated on exact times, frames as a render setting (the 2026-10-29 decision, which the 0004 draft does not yet follow in its Event model; Findings, 3 and 4).
2. **Event ties**: whether 0004's strictly increasing event lists keep their rule or take Elliott's simultaneous occurrences with a left-biased merge (Findings, 3), and the boundary rule at an event's own frame (FRP section, rows `untilB`, `stepper`).
3. **Schema looseness** in 0004: `Id`, `chapters[].sceneIds` against `scenes[].chapterId`, derivable `words` and `written` (Findings, 5).
